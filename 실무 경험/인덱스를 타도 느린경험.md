# SQL 튜닝 경험과 SQLP 개념 연결 정리

# 1. 인덱스를 탄다고 무조건 빠른 것은 아니다

실무를 하다 보면 처음에는 아래처럼 생각하기 쉽다.

```sql
인덱스 사용 = 빠름
풀스캔 = 느림
```

하지만 실제 PostgreSQL 실행계획을 보다 보면 다음과 같은 상황이 자주 발생한다.

- 인덱스를 타는데 느림
- Bitmap Heap Scan 발생
- 작은 테이블 조인인데 cost 증가
- 풀스캔이 오히려 빠름
- EXISTS가 COUNT보다 빠름
- JOIN보다 서브쿼리가 빠름

이유는 옵티마이저가 단순히 “인덱스 존재 여부”만 보는 것이 아니기 때문이다.

옵티마이저는 아래 요소들을 함께 고려한다.

- 예상 row 수(Cardinality)
- 선택도(Selectivity)
- 랜덤 I/O 비용
- Sequential Scan 비용
- 조인 횟수
- 테이블 접근 횟수
- 정렬 비용

즉 SQLP에서 배우는 개념들이 실제 실행계획에 그대로 연결된다.

---

# 2. 작은 테이블을 줄였는데 성능이 개선된 이유

튜닝 과정에서 의문이 생길 수 있다.

> “큰 테이블이 문제 같은데 왜 작은 테이블을 먼저 줄이지?”

예시:

```text
주문 테이블 : 1억 건
이벤트 대상 테이블 : 1000건
```

초보 관점에서는 보통:

```text
큰 테이블을 줄여야 한다
```

라고 생각한다.

하지만 실제 옵티마이저 관점은 다르다.

```text
1000건을 50건으로 줄이면
1억 건 테이블 접근도 50번만 하면 된다
```

즉 핵심은:

```text
큰 테이블 자체를 줄이는 것
<
큰 테이블 접근 횟수를 줄이는 것
```

이다.

---

# 3. SQLP 개념과 연결

## 3-1. 선택도 (Selectivity)

선택도는 조건을 적용했을 때 얼마나 데이터가 줄어드는지를 의미한다.

예시:

```sql
WHERE status = 'Y'
```

- 대부분이 Y라면 선택도 낮음
- 일부만 Y라면 선택도 높음

선택도가 높으면 옵티마이저는:

```text
“데이터가 많이 줄겠네?”
```

라고 판단하여 인덱스를 사용할 가능성이 높아진다.

즉 작은 테이블에서 조건으로 row 수를 줄이는 작업은 선택도를 높이는 작업과 연결된다.

---

## 3-2. Cardinality (카디널리티)

카디널리티는 조건 적용 후 예상 row 수를 의미한다.

예시:

```text
1000건 → WHERE 조건 → 50건
```

이면 카디널리티는 50으로 감소한다.

옵티마이저는 이 값을 매우 중요하게 본다.

왜냐하면:

```text
50번 접근
vs
1000번 접근
```

은 비용 차이가 매우 크기 때문이다.

즉:

```text
작은 테이블 row 감소
→ 카디널리티 감소
→ 조인 횟수 감소
→ 성능 개선
```

으로 이어진다.

---

## 3-3. Row Source

SQLP에서 Row Source는 실행계획에서 데이터가 흘러가는 단위를 의미한다.

예를 들면:

```text
Nested Loop
Hash Join
Index Scan
Bitmap Heap Scan
```

등이 모두 Row Source이다.

실행계획을 읽는다는 것은 결국:

```text
어떤 Row Source가
어떤 순서로
몇 건의 데이터를 처리하는지
```

를 이해하는 과정이다.

# 4. 왜 서브쿼리가 더 빨라질 수 있는가

실무 튜닝에서는 아래처럼 서브쿼리를 사용하는 경우가 많다.

```sql
SELECT *
FROM A
JOIN (
    SELECT id
    FROM B
    WHERE use_yn = 'Y'
) B
ON A.id = B.id
```

처음 보면:

```text
“왜 굳이 서브쿼리를 쓰지?”
```

라는 의문이 든다.

하지만 실제 목적은:

```text
조인 전에 row 수를 줄이는 것
```

이다.

즉:

```text
B 테이블 축소
→ 조인 대상 감소
→ A 접근 횟수 감소
→ 성능 개선
```

이 흐름이다.

---

# 5. Bitmap Heap Scan이 발생하는 이유

PostgreSQL에서는 데이터가 많아지면 단순 Index Scan보다 Bitmap Heap Scan이 선택될 수 있다.

이유는:

```text
Index Scan
= 랜덤 접근 반복

Bitmap Heap Scan
= 접근 위치를 모아서 한 번에 읽음
```

이기 때문이다.

즉 옵티마이저는:

```text
“건수가 많으면
한 건씩 접근하는 것보다
모아서 읽는 게 낫다”
```

라고 판단하는 것이다.

따라서:

```text
인덱스를 사용했는데 Bitmap Heap Scan 발생
```

은 반드시 나쁜 상황이 아니다.

오히려 많은 row 처리에서는 더 효율적일 수 있다.

# 6. 작은 테이블 튜닝이 중요한 이유

실무에서는 아래와 같은 방식이 자주 사용된다.

```sql
SELECT *
FROM ORDER_TABLE A
JOIN (
    SELECT DISTINCT USER_ID
    FROM EVENT_TARGET
    WHERE EVENT_ID = 'E001'
) B
ON A.USER_ID = B.USER_ID
```

핵심은:

```text
조인 전에 대상 row를 최대한 줄이는 것
```

이다.

이렇게 하면:

- Nested Loop 횟수 감소
- Index Scan 횟수 감소
- 랜덤 I/O 감소
- 전체 Cost 감소

효과를 얻을 수 있다.

즉:

```text
작은 테이블 튜닝
=
큰 테이블 접근 횟수 감소 전략
```

이라고 볼 수 있다.

---

# 7. 실무 튜닝에서 중요한 사고방식

초급 단계:

```text
인덱스 있나?
```

중급 단계:

```text
왜 인덱스를 안 타지?
```

고급 단계:

```text
왜 옵티마이저가 이 실행계획을 선택했지?
```

실무 SQL 튜닝은 결국:

- row 수 감소
- 접근 횟수 감소
- 조인 순서 최적화
- 랜덤 I/O 최소화
- 실행계획 흐름 이해

를 고민하는 과정이다.

그리고 SQLP에서 배우는:

- Selectivity
- Cardinality
- Row Source
- Optimizer
- Access Path

개념들은 모두 실제 실행계획 분석과 직접 연결된다.

---

# 8. 느낀 점 정리

이번 튜닝 경험에서 가장 인상적인 부분은 다음이었다.

```text
“큰 테이블을 직접 줄이는 것이 아니라,
작은 테이블을 줄여서
큰 테이블 접근 횟수를 줄인다”
```

처음에는:

```text
인덱스를 타면 무조건 빠르다
```

라고 생각했지만,

실제로는:

- 접근 횟수
- 예상 row 수
- 조인 순서
- 랜덤 I/O
- 선택도

등이 더 중요할 수 있다는 점을 체감하게 되었다.

또한:

```text
SQL 문법상 동일
≠
실행계획 동일
```

이라는 점도 매우 중요했다.

같은 결과를 반환하더라도:

- JOIN
- EXISTS
- 서브쿼리
- DISTINCT
- LIMIT

등의 형태에 따라 옵티마이저가 전혀 다른 실행계획을 선택할 수 있다.

결국 SQL 튜닝은 단순 문법 암기가 아니라:

```text
옵티마이저가 왜 그렇게 판단했는지 이해하는 과정
```

이라는 것을 느낄 수 있었다.
