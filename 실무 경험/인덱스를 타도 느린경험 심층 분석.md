# 인덱스를 타는데도 느린 이유 — Random Access 비용의 문제

실무에서 흔히 이렇게 생각하기 쉽다.

> “인덱스를 타면 빠르다.”

하지만 실제 운영 환경에서는 그렇지 않은 경우도 많다.

최근 특정 대상 데이터와 사용자 정보 테이블을 조인하면서 이 부분을 체감했다.

구조는 단순했다.

```text
대상 데이터의 user_id로
사용자 닉네임 조회
```

그리고 user_id에는 인덱스도 존재했다.

처음에는 성능 문제가 없을 거라고 생각했다.

- PK 성격의 조회
- 인덱스 존재
- 조건도 단순

이었기 때문이다.

하지만 실제 실행계획에서는 예상보다 비용이 크게 나왔다.

---

# 왜 느렸을까?

문제는 인덱스를 안 타는 게 아니었다.

오히려:

```text
너무 많이 인덱스를 타고 있었다.
```

구조를 단순화하면 이런 흐름이었다.

```text
대상 데이터 스캔
→ row마다 user_id 추출
→ 사용자 정보 테이블 인덱스 조회
→ 반복 수행
```

PostgreSQL 실행계획으로 보면 흔히 이런 형태가 나온다.

```text
Nested Loop
  → 대상 데이터 스캔
  → 사용자 정보 테이블 Index Scan 반복
```

핵심은 여기였다.

```text
Index Scan 자체는 빠르다.
하지만 Random Access가 너무 많아지면 비싸진다.
```

---

# Sequential Access와 Random Access 차이

DB는 연속적으로 읽는 작업에는 강하다.

예를 들면:

```text
1 → 2 → 3 → 4
```

처럼 순차적으로 읽는 방식이다.

하지만 인덱스 기반 조회는 보통:

```text
15 → 8291 → 103 → 99123
```

처럼 여기저기 점프하면서 데이터를 읽는다.

이게 바로 Random Access다.

문제는 대상 데이터가 많아질수록:

- 디스크 접근 증가
- 버퍼 캐시 부담 증가
- CPU 반복 비용 증가

문제가 커진다는 점이다.

---

# 인덱스를 타는데도 느릴 수 있는 이유

개발 초반에는 보통 이렇게 생각한다.

```text
인덱스 사용 = 성능 해결
```

하지만 실제 튜닝에서는:

```text
인덱스를 몇 번 사용하는가
```

가 훨씬 중요할 때가 많다.

특히 Nested Loop Join은:

```text
“작은 조회를 반복”
```

하는 방식이기 때문에,
반복 횟수가 커질수록 부담도 커진다.

즉:

```text
빠른 조회도
너무 많이 반복되면 느려질 수 있다.
```

---

# SQLP 개념과 연결하면

이번 사례는 SQLP 개념과도 연결된다.

## 1. Nested Loop Join

Nested Loop는 반복 인덱스 조회 기반 조인이다.

따라서:

```text
반복 횟수 증가
→ Random Access 증가
→ 비용 증가
```

구조가 된다.

---

## 2. 랜덤 I/O 비용

실제 운영 DB에서는:

```text
Random I/O가 Sequential I/O보다 훨씬 비싸다.
```

그래서 대량 인덱스 조회가 오히려 병목이 되기도 한다.

---

## 3. 카디널리티(Cardinality)

조회 대상 row 수가 많아질수록:

```text
반복 접근 횟수 자체가 증가
```

한다.

즉 카디널리티 증가는 곧 비용 증가로 이어질 수 있다.

---

## 4. Driving Table 중요성

실제 성능은:

```text
어느 테이블을 먼저 읽느냐
```

에 따라서도 달라질 수 있다.

Nested Loop Join에서는
바깥쪽 테이블의 row 수만큼
안쪽 테이블 접근이 반복되기 때문이다.

즉:

```text
Driving Table row 수 증가
→ Index Scan 반복 증가
→ Random Access 증가
```

구조가 된다.

---

# 이번 경험으로 느낀 점

예전에는 단순히:

```text
인덱스만 타면 빠르다
```

라고 생각했다.

하지만 실무에서는 오히려:

```text
반복 횟수
Random Access
Join 방식
카디널리티
```

가 더 중요했다.

특히 인상 깊었던 부분은:

```text
큰 테이블이어도
“어떻게 접근하느냐”에 따라
성능이 크게 달라진다
```

는 점이었다.

실무 튜닝은 단순히 인덱스를 추가하는 작업이 아니라:

```text
DB가 실제로 얼마나 많은 Random Access를 수행하는가
```

를 줄이는 과정에 더 가깝다는 걸 느꼈다.
