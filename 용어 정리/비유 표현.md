# 오라클 메모리 구조와 SQL 처리 흐름 비유 정리

## SGA = 교실 앞 공용 칠판

여러 학생(세션/프로세스)이 함께 사용하는 공간.

여기에 다음과 같은 공용 정보가 저장된다.

- 실행계획
- 캐시 데이터
- 로그 버퍼

특징:

- 모두가 공유
- 자주 사용하는 정보 저장
- 동시에 접근 가능
- 경쟁(Resource Contention) 발생 가능

---

# PGA = 개인 책상

학생 개인만 사용하는 작업 공간.

여기에는 다음 작업들이 들어간다.

- Sort
- Hash Join
- 세션 변수
- 커서 상태

특징:

- 다른 사람과 공유하지 않음
- 작업 종료 시 정리됨
- 접속자 수 증가 시 전체 PGA 사용량 증가

---

# Buffer Cache = 자주 보는 교과서 복사본

원본 데이터는 창고(디스크)에 있다.

하지만 매번 창고에 다녀오면 느리기 때문에
자주 사용하는 페이지를 교실에 복사해 둔다.

즉:

- 디스크 접근 감소
- 성능 향상
- 자주 사용하는 데이터 캐싱

---

# Shared Pool = 수업 자료 보관함

SQL 관련 정보들을 저장하는 공간.

---

## Library Cache = 이미 풀어본 문제 해설집

이전에 실행한 SQL의 실행계획 저장.

같은 SQL이 들어오면 다시 분석하지 않고 재사용한다.

→ Soft Parse 가능

---

# Hard Parsing = 처음 문제 푸는 과정

처음 보는 문제라 다음 작업을 모두 수행해야 한다.

- 문법 검사
- 권한 검사
- 실행계획 생성
- 비용 계산

즉,
처음부터 새롭게 문제를 푸는 과정.

비용이 크다.

---

# Soft Parsing = 기존 해설 재사용

이미 이전에 풀어본 문제라면
기존 실행계획을 재사용한다.

즉:

"전에 풀었던 문제네?"

장점:

- CPU 사용 감소
- 빠른 처리 가능

---

# Redo Log Buffer = 사건 기록 메모장

데이터 변경 내용을 임시로 기록하는 공간.

예시:

- 누가
- 언제
- 무엇을 변경했는지

기록한다.

복구를 위해 매우 중요하다.

---

# Redo Log File = CCTV 저장 서버

Redo Log Buffer 내용을 실제 디스크 파일에 저장한다.

특징:

- 전원이 꺼져도 유지
- 장애 복구 가능

---

# Undo = 되돌리기 노트

데이터 변경 이전 상태를 저장한다.

사용 목적:

- Rollback
- Read Consistency

예시:

"원래 값이 뭐였지?"

를 복구 가능하게 해준다.

---

# DB Buffer Cache Hit = 교실 안에서 바로 찾음

필요한 자료가 이미 교실(Buffer Cache)에 존재.

즉:

- 빠른 조회 가능
- 디스크 접근 불필요

---

# Physical Read = 창고 다녀오기

Buffer Cache에 데이터가 없음.

따라서 실제 디스크에서 데이터를 읽어야 한다.

즉:

- 느림
- 디스크 I/O 발생

---

# Row Source = 조립 라인 작업대

실행계획의 실제 수행 단계.

예시:

- Index Scan
- Full Table Scan
- Sort
- Hash Join
- Nested Loop

각 단계가 데이터를 다음 단계로 전달한다.

---

# Nested Loop Join = 한 명씩 대조

A 테이블의 데이터를 하나씩 꺼내며
B 테이블을 반복 탐색.

비유:

출석부 A 학생 한 명씩 꺼내서
출석부 B 전체를 확인하는 방식.

특징:

- 작은 데이터에 유리
- 인덱스 효율 중요

---

# Hash Join = 해시 맵 생성 후 빠르게 탐색

한쪽 데이터를 미리 해시 테이블로 구성.

이후 빠르게 매칭 수행.

특징:

- 대량 데이터에 강함
- 메모리 사용량 큼

---

# Sort Area(PGA 내부) = 개인 책상 위 정렬 공간

학생이 자료를 이름순으로 정렬하는 공간.

만약 공간이 부족하면?

→ Temp Tablespace 사용

---

# Temp Tablespace = 임시 창고

정렬이나 Hash 작업이 너무 커서
PGA에 담기지 않을 경우 사용하는 임시 디스크 공간.

특징:

- 디스크 사용
- 속도 저하 가능

---

# Optimizer = 문제 풀이 전략 교사

옵티마이저는 SQL을 가장 효율적으로 실행할 방법을 결정한다.

판단 요소:

- 인덱스 사용 여부
- 조인 순서
- Full Scan 여부
- 비용(Cost)

---

# 실행계획 = 문제 풀이 순서표

SQL을 어떤 순서와 방식으로 실행할지 정의한 계획.

예시:

1. 어떤 테이블부터 읽을지
2. 어떤 인덱스를 사용할지
3. 어떤 방식으로 조인할지

---

# SQLP 용어를 연결해서 이해하는 비유 정리

## 1. SGA + Shared Pool + Soft Parse

### 비유
교실 공용 칠판(SGA)에
이전에 풀어본 문제 해설집(Shared Pool)이 남아있다.

학생이 같은 문제를 다시 가져오면
새로 풀지 않고 기존 해설을 참고한다.

→ Soft Parse

---

## 핵심 연결

- SGA는 공용 메모리
- Shared Pool은 SQL 관련 정보 저장
- Soft Parse는 기존 실행계획 재사용

---

# 2. Hard Parse + Optimizer + 실행계획

### 비유

처음 보는 문제를 가져오면
선생님(Optimizer)이 가장 효율적인 풀이 방법을 고민한다.

그리고:

- 어떤 순서로 풀지
- 어떤 공식을 사용할지
- 어떤 문제부터 접근할지

결정한 뒤 풀이 순서표(실행계획)를 만든다.

이 전체 과정이 Hard Parse다.

---

## 핵심 연결

- Hard Parse는 비용이 큼
- Optimizer가 실행계획 생성
- 실행계획 품질이 성능 결정

---

# 3. Buffer Cache + Physical Read + Disk I/O

### 비유

교실 안(Buffer Cache)에 교과서가 있으면 바로 확인 가능.

하지만 없으면 창고(디스크)까지 가야 한다.

→ Physical Read 발생

즉:

- Buffer Cache Hit = 빠름
- Disk I/O = 느림

---

## 핵심 연결

- 캐시 적중률 중요
- 디스크 접근 최소화가 성능 핵심
- Full Scan 많아지면 I/O 증가

---

# 4. PGA + Sort Area + Temp Tablespace

### 비유

학생이 자기 책상(PGA)에서 자료를 정렬한다.

그런데 자료가 너무 많아 책상에 안 올라간다.

그래서 임시 창고(Temp Tablespace)에 일부 자료를 옮긴다.

---

## 핵심 연결

- Sort는 PGA 사용
- 메모리 부족 시 Temp 사용
- Temp 사용 증가 시 성능 저하 가능

---

# 5. Nested Loop + Index Scan + 랜덤 액세스

### 비유

학생이 명단 A를 한 명씩 확인하며
사전(Index)을 이용해 명단 B를 빠르게 찾는다.

하지만 사람이 너무 많아지면
계속 왔다 갔다 해야 한다.

→ 랜덤 액세스 증가

---

## 핵심 연결

- Nested Loop는 작은 건수에 유리
- Index Scan 활용
- 랜덤 액세스 많으면 느려질 수 있음

---

# 6. Hash Join + Full Scan + PGA

### 비유

학생이 데이터를 한 번에 전부 읽어온 뒤
메모장(PGA)에 해시 테이블을 만든다.

그리고 빠르게 비교한다.

---

## 핵심 연결

- 대량 데이터에 강함
- Full Scan 자주 사용
- PGA 메모리 사용량 큼

---

# 7. Undo + Rollback + Read Consistency

### 비유

학생이 문제를 잘못 수정했다.

그래서 이전 답안을 Undo 노트에서 다시 확인한다.

다른 학생들은 수정 중이어도
이전 정상 답안을 계속 볼 수 있다.

→ Read Consistency

---

## 핵심 연결

- Undo는 이전 데이터 저장
- Rollback 가능
- 읽기 일관성 보장

---

# 8. Redo Log Buffer + Commit + Recovery

### 비유

학생이 수정한 내용을 메모장(Redo Buffer)에 기록한다.

그리고 제출(Commit)하면
CCTV 저장소(Redo Log File)에 영구 저장된다.

사고 발생 시 이 기록으로 복구한다.

---

## 핵심 연결

- Commit 전에도 Redo 기록
- 장애 복구 핵심
- DB 안정성 보장

---

# 9. Optimizer + Statistics + Cost

### 비유

선생님(Optimizer)은 문제 풀이 전략을 세울 때
학생 수(통계정보)를 참고한다.

학생 수를 잘못 알고 있으면
비효율적인 풀이 전략을 선택할 수 있다.

---

## 핵심 연결

- 통계정보 중요
- Cost 기반 판단
- 잘못된 통계는 잘못된 실행계획 유발

---

# 10. Row Source + 실행계획 + 데이터 흐름

### 비유

공장에서 작업대(Row Source)가 순서대로 연결되어 있다.

- 한 작업대는 스캔
- 다음 작업대는 조인
- 다음은 정렬

이렇게 데이터를 넘기며 처리한다.

---

## 핵심 연결

- 실행계획은 작업 순서
- Row Source는 실제 실행 단계
- 단계별 데이터 전달 구조

---

# 11. Full Table Scan + Multiblock I/O + 대량 데이터

### 비유

창고 전체를 한 번에 카트로 훑는 방식.

조금씩 찾는 것보다
대량 데이터에서는 오히려 효율적일 수 있다.

---

## 핵심 연결

- 대량 조회에 유리
- Sequential I/O 사용
- 작은 건수 조회에는 비효율 가능

---

# 12. Cursor + Parse + Library Cache

### 비유

학생이 문제를 제출하면
DB는 문제 정보를 Cursor 형태로 관리한다.

이미 같은 문제가 해설집(Library Cache)에 있으면
기존 내용을 재사용한다.

---

## 핵심 연결

- Cursor는 SQL 실행 단위
- Parse 과정 필요
- 재사용 여부가 성능 차이 발생
