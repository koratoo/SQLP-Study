# 하드 파싱(Hard Parsing)과 소프트 파싱(Soft Parsing)이란?

SQL 튜닝이나 SQLP 공부를 하다 보면 자주 등장하는 개념 중 하나가 바로 하드 파싱(Hard Parsing)과 소프트 파싱(Soft Parsing)이다.

처음 보면 단순히 “SQL을 해석하는 과정인가?” 정도로 느껴질 수 있는데, 실제로는 DB 성능과 굉장히 밀접한 개념이다.

특히 Oracle 계열 DB나 SQLP 시험에서는 매우 자주 등장한다.

---

# SQL 실행 과정

DB는 SQL을 바로 실행하지 않는다.

대략 다음과 같은 과정을 거친다.

```text
1. SQL 수신
→
2. SQL 문법 검사
→
3. 실행 계획(Execution Plan) 생성
→
4. 메모리 공유 풀(Shared Pool) 확인
→
5. SQL 실행
```

여기서 “파싱(Parsing)”은 SQL을 분석하고 실행 계획을 준비하는 과정이다.

---

# 하드 파싱(Hard Parsing)

하드 파싱은:

> SQL을 처음 실행하거나,
> 기존 실행 계획을 재사용할 수 없어서
> 새롭게 실행 계획을 생성하는 과정

이다.

즉 DB가 많은 작업을 수행한다.

---

# 하드 파싱 과정

하드 파싱 시에는 보통 다음 작업들이 수행된다.

```text
- SQL 문법 검사
- 객체 존재 여부 확인
- 권한 확인
- 옵티마이저 실행
- 실행 계획 생성
- 라이브러리 캐시 저장
```

특히 옵티마이저가 실행 계획을 새로 만드는 과정이 비용이 크다.

---

# 예시

```sql
SELECT *
FROM member
WHERE member_id = 100;
```

DB가 처음 보는 SQL이라면:

```text
"이 SQL 실행 계획이 없네?"
→ 새로 분석
→ 실행 계획 생성
```

이 과정이 발생한다.

이것이 하드 파싱이다.

---

# 소프트 파싱(Soft Parsing)

소프트 파싱은:

> 이미 생성된 실행 계획을 재사용하는 과정

이다.

즉 DB가 기존 캐시를 활용한다.

하드 파싱보다 훨씬 빠르고 효율적이다.

---

# 소프트 파싱 예시

이미 아래 SQL이 실행된 적이 있다고 가정해보자.

```sql
SELECT *
FROM member
WHERE member_id = 100;
```

다시 동일 SQL이 들어오면:

```text
"이미 실행 계획이 있네?"
→ 기존 계획 재사용
→ 바로 실행
```

이 과정이 소프트 파싱이다.

---

# 왜 하드 파싱이 문제일까?

하드 파싱은 CPU 사용량이 높다.

특히:

- 옵티마이저 수행
- 실행 계획 생성
- 라이브러리 캐시 접근

등의 작업이 발생하기 때문이다.

동시에 많은 사용자가 서로 다른 SQL을 계속 생성하면:

```text
하드 파싱 증가
→ CPU 증가
→ 라이브러리 캐시 경합
→ DB 성능 저하
```

가 발생할 수 있다.

실무에서는 하드 파싱 비율을 줄이는 것이 중요하다.

---

# 바인드 변수(Bind Variable)가 중요한 이유

하드 파싱을 줄이기 위해 가장 많이 사용하는 것이 바인드 변수다.

---

# 바인드 변수 미사용

```sql
SELECT *
FROM member
WHERE member_id = 100;

SELECT *
FROM member
WHERE member_id = 101;

SELECT *
FROM member
WHERE member_id = 102;
```

값만 다르지만 DB 입장에서는 서로 다른 SQL로 인식될 수 있다.

즉 실행 계획을 계속 새로 만들 가능성이 있다.

---

# 바인드 변수 사용

```sql
SELECT *
FROM member
WHERE member_id = :member_id;
```

또는 JDBC 기준:

```java
String sql =
    "SELECT * FROM member WHERE member_id = ?";

PreparedStatement ps =
    conn.prepareStatement(sql);

ps.setLong(1, memberId);
```

이렇게 하면 SQL 구조가 동일하기 때문에 실행 계획 재사용이 가능하다.

즉:

```text
하드 파싱 감소
→ 소프트 파싱 증가
→ 성능 향상
```

효과를 얻을 수 있다.

---

# Static SQL과 Dynamic SQL

SQLP에서는 Static SQL과 Dynamic SQL도 함께 연결해서 자주 나온다.

---

# Static SQL

미리 정해진 SQL 구조를 사용하는 방식이다.

예시:

```sql
SELECT *
FROM member
WHERE member_id = :member_id;
```

특징:

- 실행 계획 재사용 쉬움
- 소프트 파싱 유리
- 안정적

---

# Dynamic SQL

조건에 따라 SQL 문자열이 계속 변경된다.

예시:

```java
String sql =
    "SELECT * FROM member WHERE 1=1";

if(name != null) {
    sql += " AND name = ?";
}

if(age != null) {
    sql += " AND age = ?";
}
```

조건 조합이 계속 달라질 수 있다.

즉:

```text
SQL 문자열 변화 증가
→ 하드 파싱 증가 가능
```

이 있다.

---

# 실무에서 중요한 포인트

실무에서는:

```text
가능한 실행 계획 재사용률을 높이는 것
```

이 중요하다.

그래서:

- PreparedStatement 사용
- 바인드 변수 사용
- SQL 구조 통일
- 불필요한 Dynamic SQL 최소화

등을 많이 고려한다.

특히 대용량 트래픽 환경에서는 하드 파싱 비율이 높아지면 DB CPU 사용량이 급격히 증가할 수 있다.

---

# SQLP 관점 핵심 정리

시험에서는 보통 이런 포인트가 중요하다.

```text
- 하드 파싱은 비용이 크다
- 소프트 파싱은 기존 실행 계획 재사용
- 바인드 변수는 소프트 파싱 유도
- Dynamic SQL은 하드 파싱 증가 가능
- 옵티마이저 수행 여부 차이 이해
```

이 정도 흐름을 이해하고 있으면 SQLP에서도 도움이 많이 된다.

---

# 정리

하드 파싱과 소프트 파싱은 단순 암기보다 “실행 계획 재사용” 관점으로 이해하면 훨씬 쉽다.

핵심은:

```text
실행 계획을 새로 만들면 하드 파싱
기존 계획을 재사용하면 소프트 파싱
```

이다.

실무에서도 DB 성능과 직결되는 중요한 개념이라 SQL 튜닝을 공부할 때 반드시 이해하고 넘어가야 하는 내용이라고 느꼈다.
